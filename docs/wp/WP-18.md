# WP-18 — Stripe Terminal adapter (server-driven)

`stripe_terminal` provider per `docs/05-PAYMENTS.md §5`, behind the WP-16 provider interface: the
register, paid hook and receipts do not change. Plain `fetch` (no Stripe SDK), API version pinned
to `2024-06-20`.

## How a Stripe sale runs

1. `sale`: create a PaymentIntent (`card_present`, `capture_method: automatic`, amount in cents,
   `usd`, `metadata {org_id, payment_id, provider_ref}`, `Idempotency-Key: filletry-pi-<ref>`), then
   `process_payment_intent` on the terminal's reader. A replayed create (same ref) is refused as a
   duplicate and never reaches the reader again.
2. Poll every second (PaymentIntent, then reader) until the PaymentIntent `succeeded` (approved;
   `amount_received` < amount = partial approval), the reader action failed with a payment error
   (declined, bank reason kept), or the reader action failed otherwise (cashier Cancel, customer
   cancel, `connection_error`).
3. **Never charge twice:** every non-success ends by *cancelling the PaymentIntent*. If Stripe
   refuses because it already succeeded, the answer is approved. A retry is a new ref, so a new
   PaymentIntent.
4. Timeout (120 s): `cancel_action`, then cancel the PaymentIntent → `cancelled` (or approved if
   the card went through meanwhile). Stripe unreachable → `indeterminate` *with the PaymentIntent
   id*. The register's immediate status check now asks about that id (`service.ts`).
5. A reader that never shows the payment (process call lost) for 10 s → PaymentIntent cancelled,
   `error` ("nothing was charged"). Reader busy / offline / unknown / bad key → `error`, and the
   PaymentIntent is cancelled.
6. `abort` sends `cancel_action` only when the reader is collecting *this* ref's PaymentIntent
   (never another register's), and returns at once. The sale's poll then reports `cancelled`.
   While a card is being authorised Stripe refuses (`terminal_reader_busy`) and the sale's own
   result stands.
7. `status(ref, txn)`: `succeeded` → approved; `canceled` → cancelled / declined; still on the
   reader → indeterminate; neither paid nor on the reader → cancel it, then report. Without a txn
   (the sale died before recording one) it searches by `metadata['provider_ref']`. Search is
   eventually consistent, so "not found" stays indeterminate.
8. Webhook: verify `Stripe-Signature` with the terminal's signing secret (Vault, by
   `config.webhook_secret_ref`). If the event names an `indeterminate` Stripe payment of that org
   (same PaymentIntent), call `status` and record a status check. Any other state is
   acknowledged (200) and left alone: the synchronous sale result is the trigger, never the
   webhook.

## Setup for a tenant (ops)

1. In the tenant's Stripe dashboard: create a **restricted key** with write access to
   PaymentIntents, Refunds, Terminal readers and Terminal connection tokens (and read access to
   Charges). Register the reader to a Location; note `tmr_…` and `tml_…`.
2. Put the key in Supabase Vault under a name, never in a table:
   `select vault.create_secret('<rk_live_…>', 'stripe_rk:<org slug>:<reader>');`
3. **Admin → Payment terminals → Add reader**: name, site, reader id, location, the Vault name
   from step 2.
4. Webhook (optional, reconciles payments the register could not confirm): in Stripe add an
   endpoint `https://<app>/api/payments/stripe/webhook/<terminal id>` (shown under the reader)
   for `payment_intent.succeeded`, `payment_intent.payment_failed` and
   `payment_intent.canceled`. Store its signing secret with
   `vault.create_secret('<whsec_…>', 'stripe_whsec:<org slug>')` and put that name in the reader's
   "Webhook signing secret" field. One endpoint per Stripe account is enough: any of the
   account's terminals can be named in the URL.

## Verify by hand (hardware / Stripe test mode)

Use a Stripe **test-mode** restricted key and a simulated reader (`simulated-wpe`) or a
physical reader with Stripe test cards.

1. Charge $1.00 at `/register` → present `4242…` (simulated:
   `POST /v1/test_helpers/terminal/readers/<tmr>/present_payment_method`) → approved, receipt
   shows brand / last4 / entry mode.
2. Charge again, present the decline card `4000 0000 0000 9995` → "Declined by the bank: …"; the
   cart stays open; Stripe shows that PaymentIntent **canceled**.
3. Charge, press **Cancel** before presenting a card → "Cancelled"; the reader returns to idle.
4. Charge and walk away → after 120 s "Timed out at the reader"; PaymentIntent canceled.
5. Unplug the reader's network, charge → "The card reader is offline".
6. Void / Refund the payment from step 1 (manager) → Stripe shows the refund.
7. With the webhook configured: during a charge, block the server's outbound access to
   `api.stripe.com` after the card is presented (or kill `pnpm dev`), so the payment ends
   `indeterminate`. Restore it. The `payment_intent.succeeded` delivery (or **Check status**)
   turns it approved.

## Assumptions and notes

- **Doc wording:** §5 says card meta comes from `charges.payment_method_details.card_present`. On
  the pinned API version the same object is the expanded `latest_charge`; docs/05 §5 now says so.
- **Partial authorisation** is mapped (`amount_received` < amount) but not requested: the
  `request_partial_authorization` option depends on the account, and sending it unenabled would
  fail every sale.
- **Restricted key enforced:** the adapter refuses a terminal secret that is not `rk_…` (the
  issue asks for a restricted key; no DECISION covers it).
- **A pending refund is not a refund.** Stripe can keep a refund `pending` (for example, the
  account balance is too low) and fail it later, and this WP reconciles no refund events. So
  `pending` is reported as `indeterminate` with the refund id. WP-16 then keeps the reversal
  reserved and unresolved, raises a critical `payment_alert`, and blocks further voids / refunds.
  A manager checks Stripe and records `refunded` or `not_reversed` with
  **Manager: resolve void/refund** (`payment_reverse_resolve`). Only `succeeded` settles at once.
- **`reverse` sends no Idempotency-Key.** It returns what is left of the payment, so Stripe itself
  refuses a duplicate (more than the remaining amount), and a stored "failed" answer is never
  replayed for 24 h. `refund` uses `filletry-refund-<ref>` (unique per refund).
- **Additive interface change:** `SaleRequest.context` carries `{orgId, paymentId}` for the
  PaymentIntent metadata. Other adapters ignore it.
- The webhook endpoint is per terminal because the signing secret lives on the terminal's config.
  A payment is reconciled only within that terminal's org, using the payment's own terminal key.
- The register UI does not do client-side reader discovery (server-driven readers don't need
  it). The connection-token endpoint exists for a future client-SDK reader.
