# WP-20 — Public customer status and transactional email

Public `/s/[orgSlug]` accepts a full phone number (the §13 full-phone option), never puts it in a URL, and calls an anonymous security-definer RPC. No staff/service credentials or private row reads are involved. All calls share an atomic per-org quota of 60/minute, including misses and direct RPC calls. This is a conservative initial limit, not a decision-default change. It deliberately trades per-org availability for a non-bypassable anonymous limiter; a busy or attacked plant may need a future second limiter dimension.

Only open sport intakes are returned: number, state, estimated pickup and the sum of that intake customer's open intake-source charges. Draft/done/cancelled intakes, names, weights, line prices, addresses and emails are excluded. This is the intake amount, not a register quote: tax, storage pickups, retail and separate angler settlements are outside this projection. Stage text comes only from `rules/customer-status.ts`. Settings supply pickup hours and a rates notice (receipt-footer fallback). §13's specific “no prices beyond amount due” governs the public projection rather than §2's general per-lb display wording.

`/admin/settings` edits pickup hours and rates notice. `/admin/notifications` lets owner/manager queue another ready email using an action id; automatic ready mail queues only once. Intake confirmation queues when an intake first leaves draft for holding (including insert-as-holding); ready queues on first stored; shipped queues on first shipment shipped with tracking. Triggers queue in the state transaction and unique event keys deduplicate repeats. Customers without an email are skipped. Templates carry the org name, notice, pickup hours (pickup emails), status link and tracking (shipped). SMS stays deferred (DECISION-08).

The saved-intake **Open customer receipt** link prints in the browser, including the status-page QR produced by `rules/qr.ts`; the shared `labels` receipt template accepts `orgSlug` too. Existing LAN intake receipt jobs have an empty PDF URL; the repository has no PDF upload/serve pipeline. That pre-existing print-agent path is not used by this browser-print flow and is not implemented here.

## Email deployment

The deployed `customer-email` Edge Function requires `RESEND_API_KEY`, `RESEND_FROM` (verified sender), and `CUSTOMER_EMAIL_DISPATCH_TOKEN` in Supabase function secrets. Configure a scheduler to POST to `/functions/v1/customer-email` every minute with `Authorization: Bearer <CUSTOMER_EMAIL_DISPATCH_TOKEN>` supplied from the scheduler's secret store. Do not place credential values in SQL migrations, URLs or logs. The existing deployment script deploys all functions; this PR does not provision credentials or an external scheduler.

Only the secret-authenticated dispatcher can claim outbox rows; anonymous users have no table access, and staff may select only their own `org_id` column (the catalog-wide tenancy probe). Delivery content and metadata are service-only. Claims lease up to 20 rows for five minutes using `SKIP LOCKED`. The first-send payload is saved before contacting Resend and reused verbatim on retries. Resend receives the stable outbox UUID as its idempotency key. Success stamps `sent_at`; failures store only an allowlisted code, never the provider body. Ten attempts maximum; automatic retry stops 23 hours after the first attempt, within [Resend's 24-hour idempotency retention](https://resend.com/docs/dashboard/emails/idempotency-keys). Inspect unsent `customer_email` rows through the authorized database operations channel; do not blindly reset attempts after that window because a lost response may already have delivered mail. Missing env leaves jobs unclaimed.
