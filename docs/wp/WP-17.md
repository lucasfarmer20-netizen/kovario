## Outcome mapping

| SPIn answer | Sale / Status result | Void (`reverse`) / Return (`refund`) |
|---|---|---|
| StatusCode `0000` / `0001` (partial, approved for `Amounts.Amount`) / `1500` | `approved` | `voided`, or `refunded` when `ProcessedAs` is Return / Refund; Return → `refunded` |
| `1012` with HostResponseCode ≠ `00` (issuer decline, terminal auto-aborted), or `1015` | `declined` + bank reason (never "cancelled") | `declined` |
| `1012` without a host code | `cancelled` | `declined` (not reversed) |
| HostResponseCode `00` on a non-approved StatusCode (conflict) | `indeterminate` → Status | `indeterminate` |
| indeterminate class, a code outside the table, `0001` without an amount | `indeterminate` → Status | `indeterminate` |
| bad_request / config_error / lookup_error | `error` (nothing charged; retry) — on **Status**: `indeterminate` (the lookup proves nothing) | `error` |
| timeout, connection reset, 5xx, unparseable body (the request may have reached the terminal) | `indeterminate` → Status | `indeterminate` (blocks new reversals until a manager resolves it — WP-16) |
| connection refused / DNS failure (nothing was sent) | `error` (retry) — on Status: `indeterminate` | `error` |
| missing / invalid terminal config (no request made) | `error` | `error` |

Classification is on `StatusCode`, never `ResultCode`.

## Manual live test checklist (real terminal — live money)

Do this on every new terminal and after any TPN / host / Authkey change, with the provisioning
runbook done (`docs/ops/dejavoo-terminal-provisioning.md`). Use **$1.00**; void everything the
same day. Record the payment numbers.

1. **Sale $1.00, chip** → register shows Approved; receipt shows brand, last 4, auth code, entry
   mode chip; the terminal printed nothing.
2. **Void it** (manager: Void, reason "live test") → payment `voided`; the iPOSPays portal shows
   the void. (If it was already batched, Filletry records `refunded` — `ProcessedAs` Return.)
3. **Sale $1.00, tap** → Approved, entry mode contactless. Void it.
4. **Cancel**: start a $1.00 sale, press **Cancel** on the register before presenting a card →
   the register unblocks at once, the terminal returns to idle, the payment ends `cancelled`.
5. **Cancel on the device**: start a sale, cancel on the terminal → `cancelled`.
6. **Decline** (only with a processor test card / test amount): → `Declined: <bank reason>`,
   never "cancelled".
7. **Timeout**: start a sale and present nothing until the terminal times out → the register
   reports the outcome via a status check (`cancelled` or indeterminate → **Check status**);
   nothing charged in the portal.
8. **Duplicate ref**: not reproducible from the register (each attempt gets a new ref) — note the
   StatusCode SPIn returns for a reused ReferenceId if the processor's sandbox lets you try it;
   the fake server assumes a bad_request code (`1013`).
9. In **Supabase → payment_event** for these payments: no `Authkey`, no full card number.
10. Portal batch totals for the day net to $0.00.

## Assumptions and notes

- **Never charge twice drives the transport mapping.** docs/05 calls 5xx / unparseable bodies
  "transport errors"; for a sale they are `indeterminate` (the proxy got the request, so the
  terminal may have charged), followed at once by Status. Only a failure before anything was
  sent (connection refused, DNS) is a retryable `error`.
- **HostResponseCode override** applies to every non-approved StatusCode: a host code ≠ `00` is
  a decline. Approved StatusCodes are not overridden (a partial approval carries host code `10`).
- **Void ReferenceId.** The `reverse` interface carries only the original ref, so the Void gets
  its own fresh ReferenceId `<original ref>-V<time base36>` plus `OriginalReferenceId` /
  `OriginalTransNum` (a ref is never reused).
- **Status** sends `ReferenceId` = `OriginalReferenceId` = the sale's ref (and `OriginalTransNum`
  when known). A Status that cannot find the sale is `indeterminate`, never "not charged".
- **Timeout.** A terminal's own timeout (30–180 s) overrides the register's 120 s wait; 180 s +
  30 s + a status call stays inside the route's 300 s `maxDuration` (DECISION-18).
- **Endpoint**: `https://<host>[:port]` only; plain http is accepted for loopback (the fake
  server / local dev) — the body carries the Authkey.
- **Terminal edits are owner-only** (stricter than other admin pages): the endpoint decides
  where the Authkey is sent. **Secret refs are `terminal:<org id>:<name>`** because
  `payment_terminal_runtime` reads Vault by name — an org can never point a terminal at another
  tenant's secret. Terminals created before this WP keep their refs (only the save path checks).
- **The Authkey is entered in Vault by ops, not in the UI** (issue: "secret ref" field). The
  register-level DB suite hands the fake server's key to the adapter directly, because the JS
  fixtures cannot write Vault; the Vault path itself is WP-16's `VAULT —`.
- Codes the fake uses for its own checks (Authkey 1017, TPN 2002, duplicate ref 1013) are its
  choice from the table, to be confirmed by checklist step 8.
