## How a payment flows

1. **Load outstanding** (`register_load_outstanding`) builds the cart on the server and replaces
   every server line (S3): draft settlements of priced sessions (the angler's or the party's),
   the customer's pending storage batches (re-quoted when stale — a new batch supersedes the old;
   a paid-unreleased batch is refused with a Force Release notice, S6; one batch that fails to load
   is reported and the rest still load, S8), and open charges that are not billed through a
   settlement or a batch. Retail lines the cashier added stay.
2. **Charge** → `POST /api/payments/sale`. As the cashier: `payment_begin` (cart row lock; refused
   while another payment of the cart is pending / indeterminate; pending payment, attempt *n*,
   `provider_ref = <order-hex-24>-<n>`, `sale_requested`). As the service role:
   `payment_terminal_runtime` (config + Vault secret by `secret_ref`), `provider.sale`, then
   `payment_record_result`. `indeterminate` (or a thrown transport error) is followed at once by a
   status check; still unknown leaves the payment `indeterminate`, which blocks the next Charge
   until **Check status** or a manager **mark** (`payment_resolve`, PIN + reason) resolves it.
   A replayed Charge (same `client_action_id`) returns the stored payment and never reaches the
   terminal again.
3. **Cancel** → `POST /api/payments/abort`: `provider.abort` and the UI unblocks at once; the
   sale's own request records the outcome.
4. **Approved**: captured amount stored (partial approval = approved for less; the cart stays open
   with the rest due); receipt snapshot stored on the payment. When nothing is due the cart turns
   `paid` and **`apply_paid_register_order`** runs.
5. **Void / Refund** (manager PIN + reason) → `payment_reverse_begin` → `provider.reverse` /
   `provider.refund` → `payment_reverse_record`: the payment becomes `voided` / `refunded` with
   the provider's txn, and a `refund` register order records amount and reason. Its hook never
   releases or settles anything (S11). **One reversal at a time:** `payment_reverse_begin`
   reserves it on the payment row (kind, amount, provider ref) and commits before the provider
   is called; a competing void / refund is refused until `payment_reverse_record` clears the
   reservation. A reservation older than the route's lifetime (its request died) can only be
   resumed as the same intent with the same provider ref, so the provider dedupes the repeat.

### The paid hook

`apply_paid_register_order(order, payment)`, one SQL function:

- settlements → `paid` (billing lock, sessions, settlements — sorted ids); when a session's
  **last** settlement is paid, its billed processing charges (`app.session_billed_charges`) settle;
- open charge lines → `settled`;
- storage batches → `app.release_pickup_batches` (S5 intake row first, S8 per-batch savepoints,
  S6 `release_failed` outside the savepoint, S2 never a second release, S12 untaxed line amount);
- `payment.settled_charge_ids`, `register_order.paid_hook_*`, `payment_event 'paid_hook'`,
  `domain_event 'register_order_paid'`; anomalies (already paid, charge not open, failure) raise a
  `payment_alert` domain event and never block siblings.

It runs on **transition** (the register calls it when the cart turns paid) and on
**insert-as-paid** (a deferred constraint trigger on `register_order` fires at commit, once the
lines and payment exist). It is idempotent: a second call returns the stored result. Payment refs
(S7): the terminal's `provider_ref` for card, the `REG-` order number for cash / check / external,
`COMP` for a COMP.

## Manual walkthrough (local)

1. `supabase start && supabase db reset`, `node scripts/web-env.mjs` (now also writes the local
   `SUPABASE_SERVICE_ROLE_KEY` the payment routes need into the gitignored `.env.local`),
   `pnpm db:demo-owner`, `pnpm db:seed-demo`, `pnpm dev`; give the demo owner a PIN in
   **Admin → Users**.
2. **Admin → Retail products**: add e.g. "Ice pack" $2.50.
3. Make something owed: a priced allocation session (`/allocate`), a pickup batch (`/storage/<id>`),
   or an open charge.
4. `/register`: find the customer → the cart lists settlements, storage pickups and charges with
   tax; add a retail line; **Tender: Cash → Record Cash** → "Paid in full"; settlements are paid,
   the storage batch is released (`/storage/<id>` shows the `REG-` ref), **Print receipt** opens
   the stored receipt.
5. Card terminals: no card adapter exists until WP-17 (Dejavoo) / WP-18 (Stripe). A
   `payment_terminal` row of those providers shows in the terminal list; charging it records an
   `error` ("adapter not available yet") and nothing is charged. The live terminal walkthrough
   (present card, Cancel on the device, decline, timeout → status) is WP-17's hardware note.
6. **Void / Refund** on a payment → reason → manager PIN: the payment shows `voided` / `refunded`;
   nothing is un-released or re-opened.

## Assumptions and notes

- **docs/04 §11 says the hook writes `release_audit`.** It does not: `release_audit` rows are fish
  movement / box finalisation (`moved | finalized | restored`, WP-15's I8–I10 read them), and a
  payment moves no fish; storage batches keep their own S7 release artifact. The hook's audit is
  `payment_event 'paid_hook'` + `domain_event 'register_order_paid'` (+ `action_log` for every
  cashier action). Flagged in the PR.
- **Session charges settle on the last settlement.** A session's pooled processing charges are
  split across settlements; they become `settled` (by the completing payment) when every
  settlement of the session is paid. Until then they are excluded from Load outstanding because
  the settlements bill them.
- **REG- numbering** (`app.sequence_prefix 'register_order'`) is new: the S7 ref of a cash release
  is the register order number.
- **Tender on `SaleRequest`** is an additive optional field so the `manual` adapter can record
  cash / check / external / COMP; card adapters ignore it.
- **Tax** applies to the whole cart subtotal (`charge.tax_code` is not consulted in v1). The admin
  settings form still writes `exclusive` only; the rule and SQL support `inclusive` / `none`.
  DECISION-07 default (compute, exclusive, cap) unchanged.
- **Refunds** never re-open settled charges or settlements and never reverse a release: the money
  goes back, the record (refund order + payment state + events) says why.
- **Late approval**: a terminal approval reported after the payment was recorded cancelled /
  declined / error is kept as approved (the money was captured) with a critical `payment_alert`.
- **Terminal admin UI** (`payment_terminal` + `secret_ref`) is not in this WP's deliverables;
  terminals are rows created by ops / WP-17. Secrets are stored in Supabase Vault under the
  `secret_ref` name and read only by `payment_terminal_runtime` (service role).
- Receipts print from the browser (like WP-09 / WP-14): there is no PDF render/upload pipeline
  for the print agent yet.
