## State transitions

The allowed edges ship as a **migration**, `supabase/migrations/20261026100100_state_transitions.sql`,
so every environment gets them with the schema (no seed step). Its content is generated from
`packages/rules/src/states.ts` by `pnpm --filter rules gen:states`, and a rules test fails
when the committed file is stale. It is one idempotent statement: it upserts every edge with
its `manager` flag (`on conflict … do update`) and deletes edges that are no longer in
`states.ts`, so re-running it leaves the table exactly equal to the generated set.

**Changing `states.ts` after this migration has been deployed:** an applied migration never
re-runs, so regenerate, then copy the generated file into a *new* timestamped migration and
point `STATE_TRANSITIONS_SQL_PATH` (`packages/rules/src/states-sql.ts`) at it. The
upsert-and-prune statement makes that new migration bring an existing database to the new
edge set.

## Automated checks

```bash
supabase start && supabase db reset
pnpm test:db
```

`supabase/tests/05_domain_schema.test.sql`:
- catalog: every domain table exists, has `pg_policies` policies and the org-scoped SELECT
  policy, maintains `updated_at`, and is not client-writable; views are `security_invoker`
  and closed to `anon`; enums are named `<table>_<col>`; every entity in the transition table has a
  guarded table;
- denormals: intake totals/ribbing across line insert/update/delete and a direct write;
  `charge.amount`; storage box counts; `storage_box_days` and S4 day counting; vessel
  location mirror; `reconcile_variance`; fulfillment rollup none → pending → partial →
  released;
- guard: `draft → stored` rejected; `holding → processing` stamps `pulled_at`; box plans
  never roll back; `force_transition` is manager-only, needs a reason, stays in the caller's
  org, writes `action_log`, replays, and leaves no bypass behind.

`00_tenancy_isolation.test.sql` (WP-02) now also sweeps every new table.
