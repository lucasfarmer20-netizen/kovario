## Lock order (every release path)

sessions → vessels → intakes, sorted ids within a level (docs/10 §11 amendment). A party's
ticked boxes are locked right after its session (they are the session's children); a freed
tag is locked with its vessel. Intake rows are locked last, inside the close gate, and
nothing is acquired after them.

| Path | Level 1 | Level 2 | Level 3 |
|---|---|---|---|
| `release_party` | the session (`FOR UPDATE`), then its ticked boxes | ticked vessels | `try_close_after_release(pooled intakes)` |
| `release_by_tag` | every non-cancelled session pooling the basket's intake | the vessel (re-read; tag must still be on it) | `try_close_after_release({intake})` |
| `restore_vessel` | sessions named by the intake's audit rows | the vessel, then its tag | the intake |

## Decisions and reconciliations (no `DECISION NEEDED` item involved)

- **P22 vs I16.** P22 reads "no partial writes; reports the stale record"; the later-amended
  I16 says a stale-but-was-valid selection is *silently dropped* and the rest applies. Built
  per I16: the stale record gets no write (no partial write *to it*), the rest applies, and
  the reply's `stale` list reports it (the screen shows it). Input faults still abort
  everything.
- **Stale by weight.** Each ticked vessel line must carry the `measure` the screen showed
  (`release_party` refuses a ticked line without it, so direct RPC callers keep the check too). A basket
  whose weight changed since (e.g. a concurrent split) is a stale selection, not an input
  fault — this is what makes P3's "re-Complete the same wizard = no-op" hold for splits.
  On the screen, a refresh that finds a changed weight drops that line's tick *and* Lbs
  Left (with a notice): the crew re-ticks against the new weight, so a refresh can never
  turn a selected split into a full pull.
- **I8 / I9 granularity.** One `moved` row per vessel acted on (`vessel_id` set), so a
  per-vessel restore nets exactly one movement. One `finalized` row per party intake per
  Complete, naming the boxes in `detail.box_numbers`. The payment ref rides `finalized` rows
  only. The CSP legacy `manual_payment_date` fallback has no Filletry equivalent (no legacy
  data) and is not built.
- **I11 / I17 scope.** A party's releasable scope is exactly the intakes its session pools.
  A vessel outside it is rejected: "pooled in ALC-…" (I17) when another live session pools
  it, else "belongs to <customer>, not this party" when the customer differs from the party
  (D4 fallback: the session's customer, else its first pooled intake's customer).
- **I12 base path.** Filletry's storage-only path is the cold-storage `storage_intake` and its
  pickup batches (WP-09, S1–S12); a storage intake cannot be pooled (no FK target), so it is
  "truly unpooled" by construction. An unpooled *processing* intake is released by tag and
  closes through the same I10 gate (P13).
- **Release on draft sessions** is refused ("price ALC-… before releasing"); cancelled
  sessions are refused (I17). `priced` and `done` sessions release; a priced session moves
  to `done` when its fulfillment rollup reads `released`.
- **No payment gate on release_party.** Settlement payment is WP-16 (unmerged); the boxing
  Complete records an optional payment ref on its `finalized` rows. Release-by-Tag has no
  payment gate by spec.
- **Restore reopens a closed intake** to `stored` through the manager-forced edge (the same
  mechanism as `force_transition`; manager-gated, reason in `action_log`), because a stored
  intake is one with an occupied basket. A tag that has since gone to another basket, or an
  archived shelf, is warn-not-block: the basket comes back untagged / unlocated.
- **Accepted residual — restore attribution after a session-less tag release.** A basket
  full-pulled by tag with no single active party writes a `moved` row with no session. Its
  restore follows the §11 rule literally (latest `moved` row of the *intake* whose session
  still nets positive), so it can net against a party whose balance came from *other*
  baskets of the same intake. That fails **closed**: the party's next box-only trip is blocked
  (I8) until the crew ticks a tote, never released without movement.
- **SMOKING SPLIT is a badge, not a link.** docs/06 asks for "SMOKING SPLIT links" in the notes
  panel; no smoking / exchange screen exists to link to yet, so the panel flags intakes with
  smoking or smoked-exchange lines and lists those lines. Turning the badge into a link is a
  follow-up for whichever package builds that screen.
- **Missing ship date under Buy Now.** I14 lifts the date *hold* only; a missing ship date is
  a blocker and survives Buy Now (P23 + P12).

## Stubs (unmerged dependencies)

- **Shipping (WP-19, #21).** Release packs ship boxes and reports each one's I13 gate
  (`held`, `blockers`, `can_buy`, `can_reprint`) plus a one-line notice in the Complete reply,
  so a held notice is never swallowed. Buying, printing, rate shopping and shipment state
  transitions (`draft → held`, …) are WP-19's; `shipment_buy_check` is the interface it calls
  before a buy or reprint.
- **Payments (WP-16).** See above; `app.try_close_after_release` is granted to `service_role`
  for the paid hook.

## How to verify by hand

1. `supabase start && supabase db reset`, `node scripts/web-env.mjs`, `pnpm db:demo-owner`,
   `pnpm db:seed-demo`, `pnpm dev`, sign in as the demo owner.
2. Take an intake through reconcile → blast → locate so it is `stored` with tagged baskets on
   shelves; at `/allocate/new` start a session for its customer with two anglers and a
   will-call box each; **Save & Price**.
3. Open `/boxing`: the party is listed. Scan the settlement receipt's boxing QR (or click).
4. The pick list shows the baskets in walk order (shelf code), the notes panel shows DIRTY /
   cut notes. Scan one basket's tag: its tick turns on. Type `5` in another basket's Lbs Left
   without ticking it and press **Complete**: refused ("Lbs Left on an unticked line").
5. Clear it, tick angler A's box, enter a payment ref, **Complete**: the box and basket
   leave the lists. Untick everything and **Complete**: "Nothing ticked".
6. Open the same party in a second tab, tick the same box there, **Complete** in tab 1, then
   tab 2: tab 2 reports it was already handled and writes nothing.
7. **Manager tools → Restore** the emptied basket with a reason: it returns to the pick list
   with its tag and shelf. **Release by tag** another basket with a reason: a warning names
   the party it is pooled in, and the release goes through.
