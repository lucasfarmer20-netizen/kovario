## Hardware verification only

1. Pair a Wave device, open `/wave`, and identify with an operator PIN.
2. With a keyboard-wedge scanner, select holding intakes (or tap Suggest FIFO fill), Create wave, then Start Verification.
3. Scan each printed numbered tote label. Check the green flash, short beep, readable confirmation and scanned/expected count; focus must return to the single scanner input after tapping controls.
4. Rescan a tote, scan another wave's tote, and scan an unknown label. Check red feedback and double buzz with the reason. The counter must not rise.
5. Disconnect the network, scan, reconnect, and wait for pending scans to drain. Select another wave before reconnecting to confirm the queued scan retains its original wave. Complete stays disabled while scans are pending.
6. At parity tap Complete — Start Processing. Confirm intakes leave holding, `pulled_at` is stamped, and the wave is done. Test wet gloves and verify all controls remain usable with 56px targets.

No dependency stubs or decision-default changes. DECISION-04's online-required scan queue is retained. Wave verification uses saved numbered tote-tag master rows; a bare intake number cannot establish which physical tote was verified.

## Review follow-up: reversible draft reservations

WP-10 retains draft reservations and implements the reviewer's option (b): **Cancel wave — Return to holding** is available for draft and verifying waves. Cancellation is atomic and replayable, clears intake assignments, preserves scan history, and never cancels a completed wave. This makes an accidental Create wave reversible. The state-machine doc's verifying lock remains the mandatory verification boundary; draft reservation is an earlier reversible selection. No DECISION default changes.

SQL tests cover both cancellation states, intake reuse, replay, completed-wave rejection, retained scan history, and wave transition timestamps. The UI test exercises the cancel RPC.
