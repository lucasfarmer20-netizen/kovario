## Search

- From **3 digits** (any formatting: `(907) 555-`, `907555`, `+1907…`) it matches anywhere in
  `phone_digits`. Ranking: exact number, then prefix of the number with or without the `1`
  country code, then substring matches, then most recent visit.
- Without 3 digits, **3+ letters** match names (`ilike`, trigram index; `%`/`_` are literal).
- Anything else (empty, `(`, `+1`, 500 characters, …) returns no rows; nothing raises.
- `security definer` and org-pinned: an end-user session only ever searches `app.org_id()`
  (another `p_org_id` returns nothing); `anon` cannot call it. Definer because under RLS
  Postgres does not push the non-leakproof `LIKE` into an index, and every search would
  seq-scan.
- Phones match with `strpos()`, not `LIKE`, on purpose: digit trigrams are unselective when
  one area code dominates (`190`/`907` sit in nearly every row), so the trigram index was up
  to ~300 ms where scanning the org's rows takes ~10 ms. Whether the planner picked it
  depended on ANALYZE's sample, which made it flaky. The WP-03 phone trigram index is
  left in place, unused by this search.

## Lodge-guest flip (reprice hook)

`set_lodge_guest(client_action_id, customer_id, is_lodge_guest, lodge_id?)` locks the
customer, updates it and — when `(is_lodge_guest, lodge_id)` actually changes — writes
`domain_event(kind = 'customer_lodge_flag_changed', subject_id = customer, payload =
{is_lodge_guest, lodge_id, previous_is_lodge_guest, previous_lodge_id})` in the same
transaction. WP-07's reprice consumes it (open, unpaid, non-Fast-Pass processing charges;
docs/04 §2). Clients cannot update `customer` directly, so the event cannot be bypassed.
Turning the flag off clears the lodge; turning it on without a lodge keeps the current one.

## Merge duplicates

`admin_merge_customers(keep, merge)` re-points every FK to `customer` (found from the
catalog, so later tables are covered), moves pending `customer_*` events, fills the kept
customer's empty email/phone/address, keeps the latest visit, deletes the merged row and
writes `customer_merged`. It refuses two different phones, and two different lodge statuses
(flip one through `set_lodge_guest` first, so a merge never silently moves charges between
pricing tiers).

## Automated checks

```bash
supabase start && supabase db reset
pnpm test:db          # 06_customers.test.sql + customer-search.db.test.ts
pnpm -r test          # rules phone.test.ts, web customer-search-state.test.ts
```

- `supabase/tests/06_customers.test.sql` — partial/formatted phone input (`(907) 555-`,
  `907555`, `+1907`, full national and E.164, middle and last digits, foreign), ranking,
  lodge badge, limit clamp, name fallback incl. LIKE wildcards, a list of odd partial inputs
  that must neither raise nor return rows, org pinning, anon denied; inline create (replay,
  E.164 constraint, roles); lodge flip writes exactly one event per change, replay, clears
  the lodge, cross-org/invalid input; admin edit, duplicates, merge (FK re-pointing, events,
  refusals, replay); lodge create/update (unique name, cap ≥ 0 or none, cross-org).
- `packages/db/src/customer-search.db.test.ts` — **acceptance:** seeds **50k customers** (80%
  in one area code, the worst case) with no VACUUM, then times nine query shapes through
  PostgREST as a staff session; the median of 5 runs must be **< 150 ms** for each (locally
  7–30 ms in SQL).
- `apps/web/components/customers/customer-search-state.test.ts` — search thresholds, keyboard
  highlight wrap, inline-create draft/validation, scanner burst vs. human typing.

`/admin/customers`: type `(907) 555-` → dropdown with name, phone, last visit and lodge badge;
↓/↑ + Enter opens a customer; the last option (“New customer…”) creates one inline.

`customer_lodge_flag_changed` row appears in `domain_event`.
