# Filletry — Architecture

## 1. Stack (fixed for v1)

| Layer | Choice | Notes |
|---|---|---|
| Web app | **Next.js (App Router), TypeScript strict, React 19** | Single app; stations are routes under `/app/(station)/…` served as a PWA |
| UI | Tailwind + shadcn/ui, large-target "station" variants | Station screens: ≥ 56px tap targets, high contrast, no hover-only affordances |
| Data | **Supabase Postgres** with **RLS per `org_id`** | Migrations in `supabase/migrations/*.sql`, SQL only, idempotent |
| Auth | Supabase Auth (email/password + magic link) | Staff users; **station devices** use a device session (see §5) |
| Server logic | Next.js Route Handlers + Server Actions for app logic; **Supabase Edge Functions** for secret-holding integrations (payments, Shippo) | Secrets never reach the browser |
| Realtime | Supabase Realtime (Postgres changes) | Queues refresh live; print agent subscribes to `print_job` |
| Validation | zod everywhere at boundaries; DB constraints as the last line | |
| Testing | vitest (unit + rules engine), Playwright (e2e smoke), pgTAP optional for RLS | |
| Hosting | Vercel (app), Supabase (DB/functions) | |
| Billing | Stripe Billing | Tenant subscriptions only — not card-present |
| Offline | **Not in v1** (DECISION-04). Scan actions go through a client-side **scan queue** with retry + idempotency keys | PowerSync is a later WP behind the same data-access layer |

Package manager: **pnpm**. Node 22+. Monorepo layout is a single Next app plus a
`packages/` folder for pure libraries:

```
filletry/
  apps/web/                 # Next.js app (stations, admin, register, public status)
  packages/rules/           # pure TS: processing rules, yield, pricing, state machines
  packages/payments/        # provider interface + adapters (no React)
  packages/labels/          # ZPL + PDF label/receipt templates
  packages/db/              # generated Supabase types, typed query helpers
  packages/shipping/        # Shippo client
  agent/print-agent/        # Node service for the plant LAN (printers, scale)
  supabase/                 # migrations, seed, edge functions
  docs/                     # this spec
```

## 2. Request flow by kind

```
Browser (station PWA) ──server action / route──▶ Next.js (Vercel) ──supabase-js (RLS, user JWT)──▶ Postgres
Browser ──never──▶ card terminal / printer / scale
Next.js or Edge Function ──HTTPS──▶ Dejavoo SPIn cloud / Stripe / Shippo (secrets in Vault/env)
Print agent (plant LAN) ──Realtime subscribe──▶ print_job rows ──TCP 9100 ZPL──▶ Zebra
Print agent ──serial──▶ scale ──insert──▶ scale_reading rows ──Realtime──▶ reconcile screen
```

## 3. Tenancy

- Every domain table has `org_id uuid not null references org(id)`.
- RLS on every table: `org_id = app.org_id()` where `app.org_id()` (schema `app`, ours —
  never create objects in Supabase's managed `auth` schema) reads the JWT custom claim
  `org_id` set by a Supabase Auth hook. A user in several orgs gets the org marked
  `is_default` on `org_member`; an org switcher re-mints the session. Service-role is
  used **only** in Edge Functions, the print agent's scoped key, and the payment/
  shipping route handlers listed in `docs/05-PAYMENTS.md` / `docs/07-INTEGRATIONS.md`.
- `org_member(org_id, user_id, role)` roles: `owner`, `manager`, `staff`, `cashier`.
  Managers gate: void/refund, price overrides, manual state changes, release-by-tag.
- Sequences are **per org**: `next_seq(org_id, kind)` with prefixes INT (intake), STG
  (storage intake), SPB (storage batch), WAVE, CHG (charge), ALC (allocation session),
  STL (settlement), BOX (box plan), SHP (shipment), PAY (payment), FA (audit batches),
  generated by a SQL function (row-locked counter table, not Postgres
  sequences, so numbering is tenant-local and gap-free enough for paper).

| `/admin/*` | Settings, pricing, locations, tags, users, devices | keyboard |

Every scan station uses the shared `<ScanInput>` primitive: always focused, captures
keyboard-wedge input terminated by Enter, debounces, shows green/red + audio feedback,
writes a `scan_log` row for every scan (hit or miss), and never loses focus to a modal.

## 5. Devices and operators

Shared tablets don't log in as a person. A **device** record (per org, per station) is
registered once by a manager (QR pairing). Each device is backed by a real
`auth.users` row (`device-<id>@devices.filletry.internal`) so RLS and `app.org_id()`
work uniformly; the pairing flow signs that user in and stores the session on the
device. Postgres roles stay `anon`/`authenticated`; **`app_role`** is a JWT claim
(`owner|manager|staff|cashier|station|agent`) checked by RLS policies and server
code. Operators identify by a 4–6 digit PIN at the station; `scan_log.operator_id`
records who. Manager actions require a manager PIN prompt that mints a short-lived
elevated token (Edge Function).

## 6. Integrations boundary

All external calls live in `packages/payments`, `packages/shipping`, or Edge Functions,
behind interfaces defined in `docs/05-PAYMENTS.md` and `docs/07-INTEGRATIONS.md`.
Nothing in `apps/web` imports a vendor SDK directly.

## 7. Idempotency and locking (how we avoid CSP's bug classes)

- Every mutating action takes an **idempotency key** (`client_action_id`) stored in
  `action_log`; a replay returns the stored result.
- Multi-row money/release actions run in a **single Postgres function** (`security
  definer`, RLS-checked by explicit `org_id` guard) that locks rows in a fixed order:
  **session → vessels → intakes** (`select … for update`, sorted ids), re-reads state,
  then writes. Never lock in the app layer across round trips.
- Derived fields are either **computed views** or maintained by **triggers** — never
  "stored computes" recalculated by app code (CSP's stale `@api.depends` lesson).

## 8. Environments

- `local` — `supabase start` + `pnpm dev`; seeded demo org `demo-plant`.
- `preview` — Vercel preview per PR for UI review only, pointed at `staging` Supabase
  with a throwaway demo org (Supabase per-PR branches are post-v1).
- `staging` — long-lived; CSP trial tenant.
- `prod` — `app.filletry.com` (DECISION-16).

## 9. Observability

- Structured logs (pino) with `org_id`, `station`, `action_id`.
- Every integration call logs scrubbed request/response (`Authkey`, PAN, tokens
  redacted centrally — one scrub function per adapter).
- `action_log` + `scan_log` + `release_audit` + `payment_event` are the audit spine.
